# ztest

测试策略设计 skill:**读方案 → 出测试计划 → 分层策略 → 覆盖率目标 → 写入 openspec change**。

定位对称:`zarchitect` 出技术方案,`ztest` 出验证方案。两者互补——方案决定"做什么",测试策略决定"怎么证明做对了"。

## 何时触发
- 用户说"怎么测"、"测试方案"、"覆盖率"、"test plan"、"怎么保证质量"
- zarchitect 出方案后自动触发(出测试计划)
- zapply 开 change 后自动触发(为每个 change 补测试策略)
- Bug 修复、性能优化、增量需求等任何需要写代码的场景

## 工作流

### 1. 读方案
读取目标 change 目录下的现有文档:
- `proposal.md` — 理解需求和目标
- `design.md` — 理解技术方案和模块划分
- `tasks.md` — 理解实施任务拆解

没有现成方案时:
- 用 `Explore` 扫描代码库理解现有架构
- 读取相关模块的代码和已有测试
- 必要时找用户确认需求边界

### 2. 分析测试边界
基于方案输出:`需求/问题清单 + 拆解结构 + 关键风险`

- **产品漏洞检查**:逻辑闭环、边界条件、异常流、用户场景覆盖
- **需求拆解**:按模块/层次拆解,识别依赖关系和优先级
- **现有代码对照**:兼容性、影响面、技术债
- **性能考量**(如适用):瓶颈在哪、优化空间、trade-off
- **设计模式建议**(如适用):适用场景、模式选型、侵入程度

### 3. 输出测试策略
在 `openspec/changes/<slug>/test-plan.md` 写入完整测试计划:

**测试策略**
- 分层策略:单元 / 集成 / E2E 各覆盖什么
- 覆盖率目标:核心模块/非核心模块的分层目标
- 测试数据方案:fixture / mock / 真实数据 / 工厂模式
- 边界/异常/并发场景清单
- 性能测试(如适用):压测场景、阈值、工具

**测试用例矩阵**
| 模块 | 场景 | 类型 | 优先级 | 预期结果 |
|------|------|------|--------|----------|
| ... | ... | 单/集/E2E | P0/P1/P2 | ... |

**实施建议**
- 建议的测试框架和工具
- 目录结构建议
- Mock/Stub 策略
- 测试环境要求

### 4. 画图（图文并茂，必须）
使用 `diagram-design` 技能生成测试相关图表:
- **测试金字塔**:展示单/集/E2E 比例
- **数据流图**:展示测试数据如何流入/流出
- **架构图**(如适用):展示测试环境和生产环境的隔离

图产出后放在项目目录下,并在 test-plan.md 中引用路径。

### 5. 交付
输出:`test-plan.md` + 测试用例矩阵 + 图示 + 覆盖率目标 + 实施建议

## 输出格式
```markdown
# Test Plan — <change 标题>

## 测试策略
<分层策略 + 覆盖率目标 + 测试数据方案 + 边界/异常/并发场景>

## 测试用例矩阵
| 模块 | 场景 | 类型 | 优先级 | 预期结果 |
|------|------|------|--------|----------|
| ... | ... | 单/集/E2E | P0/P1/P2 | ... |

## 性能测试（如适用）
<压测场景 + 阈值 + 工具>

## 实施建议
<测试框架 + 目录结构 + Mock 策略 + 环境要求>

## 图示索引
| 图 | 路径 | 说明 |
|---|---|---|
| <测试金字塔> | <路径> | <展示单/集/E2E 比例> |
```

## 约束
1. 只出测试策略,不写测试代码——代码由 craftsman 按 TDD 执行
2. 测试计划写入 `openspec/changes/<slug>/test-plan.md`,不放在自定义目录
3. 测试用例必须覆盖边界条件、异常流、并发场景——不能只测 happy path
4. 覆盖率目标必须量化,不能写"尽量覆盖"——核心模块必须有明确百分比
5. 测试金字塔必须可视化——没有图视为不完整
6. 测试计划是方案的必要组成部分,不是可选项——zarchitect 出方案后必须补齐
