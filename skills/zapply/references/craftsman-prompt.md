# Craftsman 执行 Prompt 模板

zapply 第 2 步下发子智能体时使用。填充占位符(`<...>`)后,整体作为子智能体的任务描述。

## 首次下发模板

```markdown
## 上下文

- Change 路径:<change-dir>
- 方案约束:<设计约束摘要——必做的、明确不做的>
- 任务清单:<tasks.md 全量内容>

## 任务

1. 创建分支 <change-name>(已存在且无未合并提交 → 复用或重建;有未合并提交 → 停下报告,不要动它)
2. 按 tasks.md 逐项实现,严格遵循方案约束
3. 每完成一项,立刻在 tasks.md 勾选对应 checkbox
4. 运行项目测试/lint,失败就修到通过;修不动就如实报告
5. 返回执行报告

## 执行原则

- 只改代码 + 勾选 tasks.md;禁止修改 proposal.md / design.md
- 设计歧义:按最小惊讶原则实现,并在报告中标注"歧义点 + 我的选择"
- 不创建与任务无关的优化/重构;拿不准的改动不做,列入报告

## 交付物(必须全部返回)

- 分支名
- 修改文件列表(git diff --name-only)
- 测试/lint 输出(通过/失败摘要)
- 任务完成度(x/y)
- 未完成项与原因、风险、歧义点
```

## 重跑变体(第 3 步 verify 失败后)

在首次模板基础上,**追加**以下两节(不要删首次模板):

```markdown
## 上一轮结果

- 核实差异:<openspec validate 结果 + code review 全量条目——blocker 优先、suggestion 次之,各带「文件:行 + 问题」>
- 用户决策:<方向——重跑 / 修某处 / 范围调整>

## 本轮要求

1. 先解决 blocker,再处理 suggestion,最后继续未完成任务;suggestion 确实不该修的说明理由,不许静默跳过
2. 报告时逐条回应上一轮差异:每项 = 已修 / 无法修(原因)/ 判定不属于本轮范围(理由)
3. 其余执行原则与交付物同首次
```

## 使用说明

- 分支命名 = change 名(如 `2026-08-20-add-export`),与 openspec change 同名,便于关联
- 用户选择"手动修"时,主智能体自己修,不再下发 craftsman
- 用户选择"中止"时,结束流程;分支保留,供后续恢复
