# Code Reviewer 审查 Prompt 模板

zapply 第 3 步核实阶段(3b),起 code-reviewer 子智能体时使用。填充占位符(`<...>`)后,整体作为子智能体的任务描述。

## 模板

```markdown
## 上下文

- Change 路径:<change-dir>
- 审查范围:<分支名> 相对 base 的完整 diff
- 方案约束:<设计约束——必做的、明确不做的、架构/分层约定>
- Craftsman 交付报告:<其报告要点——改动文件 / 测试结果 / 声明完成的任务>

## 任务(只读,不修改任何文件)

1. 核对 diff 是否偏离设计约束:该做的没做、不该做的做了
2. 找 bug / 逻辑错误 / 边界遗漏 / 安全问题(注入、越权、敏感信息泄漏)
3. 代码设计与架构合理性:遵循项目现有分层/模块约定?过度耦合、循环依赖、不合理抽象?公共接口/工具函数签名与项目风格一致?
4. 设计原则与模式应用:单一职责(SRP)、开闭(OCP)、依赖倒置(DIP)、最少知道(Demeter)?策略/工厂/观察者等模式恰当使用而非滥用?重复代码可抽象?
5. 硬编码与死代码:魔法值/硬编码路径/URL/凭证(硬编码凭证 = blocker)?未使用的 import/变量/函数/参数、注释掉的代码块、不可达分支、调试残留(log/TODO/FIXME)?
6. 错误与资源处理:异常被吞(catch 后不处理不打日志)?资源(连接/流/文件句柄)未释放?错误处理模式与项目既有约定一致?
7. 性能隐患:N+1 查询、循环内 IO/重复计算、不必要的全量加载、大对象拷贝
8. 测试与兼容:新增逻辑有测试覆盖?公共接口有无破坏性变更、调用方是否同步改?
9. 代码风格与整洁度:命名清晰?函数/类单一职责?过长函数/过深嵌套?注释必要且不过度?
10. 核对 craftsman 报告是否属实:声明的任务真的实现了吗?测试结果可信吗?

## 输出格式

按严重度分级,每条给「文件:行 + 问题 + 理由」:

- **blocker**:必须修才能归档(bug / 安全问题 / 硬编码凭证 / 明显偏离方案约束 / 破坏性变更)
- **suggestion**:不阻塞归档(风格 / 微优化 / 可读性)

没有 blocker 就明说"未发现 blocker",不要为了凑数报低价值问题(置信度过滤)。
```

## 使用说明

- **只读**:code-reviewer 不写任何文件,只返回审查报告;发现的问题由主智能体决定谁修
- **独立**:审查者不偏袒 craftsman 的自报,也不受主智能体"希望通过"的心态影响
- **门禁**:blocker 是归档硬门禁;suggestion 不阻塞,汇总给用户看
- 用户选择"重跑 craftsman"时,blocker 条目逐条进入重跑 prompt 的"上一轮结果"
