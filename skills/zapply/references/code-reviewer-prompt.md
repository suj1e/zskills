# Code Reviewer 审查 Prompt 模板

zapply 第 3c 步代码审查的**两用文档**:

1. **降级路径任务模板**:未安装 `zapply-reviewer`(zagents)时,填充占位符(`<...>`)后整体作为**内置 code-reviewer** 的任务描述。
2. **维度权威源**:本清单与 `zagents/agents/zapply-reviewer.md` 内置清单**镜像维护**——在这里改维度,必须双向同步到那边。

> ⚠️ 若已装 `zapply-reviewer`:它**自含同款清单与分层机制**,dispatch 时只给上下文四要素(change 路径 / 审查分支 / 方案约束 / craftsman 报告要点),**不要**把本模板正文灌给它,否则两套指令互相打架。

## 模板

```markdown
## 上下文

- Change 路径:<change-dir>
- 审查范围:<分支名> 相对 base 的完整 diff
- 方案约束:<设计约束——必做的、明确不做的、架构/分层约定>
- Craftsman 交付报告:<其报告要点——改动文件 / 测试结果 / 声明完成的任务>

## 任务(只读,不修改任何文件)

1. 核对 diff 是否偏离设计约束:该做的没做、不该做的做了;UI 任务另核对是否严格遵循项目 DESIGN.md——视觉量经 CSS 变量消费、无硬编码 hex/px 新值、无与既定品牌冲突的样式决策
2. 找 bug / 逻辑错误 / 边界遗漏(空/null、空集合、日期时区、字符编码)/ 安全问题(注入、越权、敏感信息泄漏)
3. 代码设计与架构合理性:遵循项目现有分层/模块约定?过度耦合、循环依赖、不合理抽象?公共接口/工具函数签名与项目风格一致?
4. 设计原则与模式应用:单一职责(SRP)、开闭(OCP)、依赖倒置(DIP)、最少知道(Demeter)?策略/工厂/观察者等模式恰当使用而非滥用?重复代码可抽象?
5. 禁止魔法常量(重点):业务相关的魔法数字/字符串——阈值、超时、重试次数、分页大小、状态码、枚举值、开关——必须提为命名常量或配置项,写死 = blocker;循环边界(i=0、len-1)等自明的除外。硬编码路径/URL 同理,硬编码凭证 = blocker
6. 禁止造轮子(重点),按阶梯核查:① 语言标准库 / 项目已有工具 / 已引入依赖能覆盖(如 deepClone、日期格式化、防抖节流、retry、参数校验)却手写重实现 = **blocker**;② 需求非平凡(日期时区/加密/解析/校验等易错领域,或手写数十行)却既不引成熟库也不用标准库、执意手写 = **suggestion**(要求引入成熟库或说明理由);③ 反向小题大做——几行能解决的琐事引入重库 = **suggestion**;④ craftsman 擅自引入**框架级重依赖** = **blocker**(超出执行权限,应停下报告由方案层拍板);确需自造(依赖不满足/性能/引库过重)必须在报告中说明理由
7. 死代码与残留:未使用的 import/变量/函数/参数、注释掉的代码块、不可达分支、调试残留(log/TODO/FIXME)?
8. 错误与资源处理:异常被吞(catch 后不处理不打日志)?资源(连接/流/文件句柄)未释放?错误处理模式与项目既有约定一致?
9. 并发与数据一致性:共享状态无保护(竞态)?漏 await 的异步调用?多步写操作无事务、部分失败留脏数据?
10. 性能隐患:N+1 查询、循环内 IO/重复计算、不必要的全量加载、大对象拷贝
11. 测试与兼容:新增逻辑有测试覆盖?测试是否遵循 design.md「测试策略」章节的分层/覆盖率目标/场景要求(边界/异常/并发)?公共接口有无破坏性变更、调用方是否同步改?
12. 依赖与文档同步:新增依赖是否必要、版本是否锁定、成熟度如何(社区活跃/维护状态/周下载量级)、有无弃用/已知漏洞?选型是否贴合项目现有生态(同领域已有同类库还引第二个 = blocker)?行为变更是否同步了 README/API 文档/接口注释?
13. 代码风格与整洁度:命名清晰?函数/类单一职责?过长函数/过深嵌套?注释必要且不过度?
14. 核对 craftsman 报告是否属实:声明的任务真的实现了吗?测试结果可信吗?

> 维度按项目技术栈裁剪:不适用的(如无数据库则无 N+1、纯前端无事务)明说跳过,不为凑数硬找问题。

## 输出格式

按严重度分级,每条给「文件:行 + 问题 + 理由」:

- **blocker**:必须修才能归档(bug / 安全问题 / 硬编码凭证 / 业务魔法常量 / 重复造轮子 / 明显偏离方案约束 / 破坏性变更)
- **suggestion**:同样下发修复,优先级低于 blocker(风格 / 微优化 / 可读性);确实不该修的由 craftsman 说明理由

没有 blocker 就明说"未发现 blocker",不要为了凑数报低价值问题(置信度过滤)。
```

## 使用说明

- **只读**:code-reviewer 不写任何文件,只返回审查报告;发现的问题由主智能体决定谁修
- **独立**:审查者不偏袒 craftsman 的自报,也不受主智能体"希望通过"的心态影响
- **门禁**:blocker 是归档硬门禁;suggestion 不改变门禁,但同样下发 craftsman 修复,逐条处理(修复或说明理由)
- 用户选择"重跑 craftsman"时,blocker + suggestion **全量**进入重跑 prompt 的"上一轮结果",标注优先级:blocker 先、suggestion 后
