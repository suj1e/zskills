# zdoc

文档 skill:**读源码/设计 → 梳理结构 → 写文档 → 图文并茂 → 输出完整文档**。

## 何时触发
- 用户说"写文档"、"更新 README"、"写 API 文档"、"changelog"、"文档整理"
- 新功能上线后需要写文档（README、API 文档、使用指南）
- 架构变更后需要更新架构文档或迁移指南
- 代码注释过少或过时，需要补充/整理
- 需要写 changelog（版本变更记录）
- 需要写 onboarding 文档（新成员上手指南）
- 需要整理现有文档，统一风格和结构
- architect 出完设计方案后，需要把方案转化为可读的设计文档

## 工作流

### 1. 接单：明确文档类型和目标读者
和用户确认：
- 文档类型（README / API 文档 / changelog / 迁移指南 / 代码注释 / 设计文档）
- 目标读者（终端用户 / 开发者 / 运维 / 新成员）
- 输出格式（Markdown / HTML / 其他）
- 输出路径（如已知）

### 2. 收集素材
- 用 `Read` 阅读源码、注释、设计文档
- 用 `Explore` 子智能体扫描代码库，理解整体结构和模块职责
- 用 `WebSearch` / `WebFetch` 查外部资料（同类项目的文档风格、行业规范）
- 查看现有文档的风格、术语、结构，保持一致性

### 3. 梳理结构
确定文档大纲和关键要点，用层级列表展示给用户确认（特别是长文档）。

### 4. 撰写
用清晰的语言写文档，保持术语一致。

### 5. 画图（图文并茂，必须）
使用 `diagram-design` 技能生成文档所需的图表：
- 架构图（architecture）—— 展示系统整体结构
- 流程图（flowchart）—— 展示业务流程
- 时序图（sequence）—— 展示交互顺序
- ER 图（erd）—— 展示数据模型
- 数据流图（data-flow）—— 展示数据流转

图产出后:服务于 openspec change 的放对应 change 目录下的 `diagrams/`;README、changelog 等独立文档的配图回落 `docs/diagrams/`。在文档中引用相对路径。
如果文档涉及页面/UI 设计，使用 `zdesign` 技能生成带品牌风格的 HTML/CSS 设计稿。

### 6. 自检
- 检查是否有遗漏、是否有错误
- 检查是否符合目标读者的理解水平
- 检查图是否都正确引用
- 检查术语是否一致
- 检查代码示例是否与实际代码一致

### 7. 交付
输出完整文档,自检通过后交付。

## 待补充（可选）

## 约束
1. 不修改代码、不执行 Git 操作——只输出文档内容，由 craftsman 或主智能体写入文件。
2. 保持与现有文档的风格一致（术语、格式、语气），不要引入全新的风格。
3. 不编造 API 行为或代码逻辑——不确定的先读源码，读不懂的写「待确认」。
4. 面向用户的技术文档避免内部实现细节；面向开发者的文档可以包含实现细节。
5. 文档中的代码示例必须与实际代码一致，不能写"示意代码"代替真实代码。
6. changelog 必须按时间倒序，每个条目写明变更类型（feat / fix / refactor / docs 等）。
7. 文档必须图文并茂——没有图的 README / 设计文档视为不完整。
