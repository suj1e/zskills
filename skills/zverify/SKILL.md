# zverify

功能点 ↔ 代码实现一致性核查 skill:**三入口 → 拆命题 → 取证 → 逐项裁定 → 会话内汇报**。

汇报就是交付物——默认零落盘,用户明确要存档才写文件。

## 三入口(汇入同一管道)

- **口述入口**:用户直接丢一段逻辑(如"登录后应该能看到历史订单,能取消未支付的")——原话就是素材,直接进拆命题。
- **文档入口**:用户指定产品文档(docx/pptx/xlsx/md/pdf)——先抽取成逻辑条目(每条 = 功能描述(原文摘录) + 出处段落),再走同一拆命题管道。
- **探索入口**:用户只点名范围不给逻辑("核实一下支付这块")——skill **先起草清单**:从需求源(openspec specs / docs / PRD / 领域常识)提取该范围应有的功能点,**展示给用户增删确认后**才作为命题进取证。
- 三源可混合;文档源多文档时先扫跨文档冲突/重复项,有则先向用户披露。

### 探索入口的起草铁律

起草清单**禁止以实现代码为来源**——先扫代码起草,清单只会包含已实现的,❌ 永远为零,核查退化为照抄现状。清单只能来自需求侧文档与领域常识;代码结构(模块/路由)仅用于圈定范围边界。需求源完全缺失时,用领域常识起草并**显式声明"该范围无需求文档,清单基于常识"**,请用户从严增删。

## 工作流

### 1. 拆命题(核心加工)
把逻辑描述(或探索入口经用户确认的清单项)拆成可独立判真伪的原子命题——一句话一个行为/事实:
- **判据按类型自动分层,默认不问**:
  - 行为/逻辑类 → "代码中存在贯通的实现链路"(路由/调用/落库齐备;只有空壳函数不算)
  - UI 类 → "可达且可见"
  - 数据类 → "字段、接口、流转三齐"
  - 测试覆盖类(用户点名时) → "测试存在**且断言了关键行为**"(只报测试名不算)
- 仅**真歧义**才发问(影响取证范围的,如"历史订单"是全部还是近 30 天),整轮 ≤ 2 个问题
- 命题 ≤ 5 条:展示清单直接进下一步;更多:展示清单请用户扫一眼确认无漏再继续

### 2. 取证计划
按模块/域聚类命题(相邻的归同一代理);为每项列预期证据锚点(路由 / 组件 / 数据表 / 配置键 / 测试名)。
**≤ 5 条命题单个代理直查即可,不为并行而并行。**

### 3. 并行取证
超阈值或跨模块时,**后台派发只读探索子智能体**(Explore / code-explorer,按聚类分组;未装则主智能体自查),每个代理的指令包含:
- 所辖命题 + 各项判据 + 项目技术栈提示
- 证据返回格式:`文件:行` + 关键代码摘录(≤5 行) + 置信度(高/中/低)
- 铁律:**只陈述找到的证据,禁止臆断"应该有"**

### 4. 逐项裁定(四态)
- ✅ 已实现 / 🟡 部分实现(缺什么) / ❌ 未找到实现 / ⚠️ 实现但与描述不符(偏差点)
- **低置信度项必须二次复核**(换关键词/换代理再查一轮)后才允许下 ❌——漏报比多查代价高

### 5. 会话内汇报(默认零落盘)
- 总览统计(✅a / 🟡b / ❌c / ⚠️d)
- 逐项对照表:命题 | 判定 | 证据(文件:行) | 差距说明
- **降载**:命题 > 30 项时,✅ 折叠为统计,详表只展开 ❌/⚠️/🟡
- **差距清单**(❌+⚠️+🟡 缺口汇总)——只列出不流转,转不转 zarchitect 由用户点名
- 用户明确要存档 → 才落盘(路径听用户的),commit 与否也听用户

## 边界
- 只读核查:可运行测试/构建作为辅助证据,不改任何源码
- 不开 change、不修复——差距修复走 zarchitect → zapply,由用户点名发起
- 核查默认**零落盘**——不产生任何文件,自然无 commit 之扰
