# zverify

功能点 ↔ 代码实现一致性核查 skill:**提功能点 → 定判据 → 并行取证 → 逐项裁定 → 报告落 `.zdev/verify/`**。

输入双源平等:**产品文档**（docx/pptx/xlsx/md/pdf）或**用户口述清单**。回答的永远是同一类问题:"这个功能真的做了吗？做到什么程度？"

## 何时触发
- 用户说"核实实现"、"实现了吗"、"实现了多少"、"对照产品文档核一遍"、"功能清单核对"
- 有产品文档，想知道实际实现情况（如"报告里的图表实现，我需要一一核对"）
- 上线前抽查某些功能是否真的交付

## 工作流

### 1. 提功能点清单（双源平等）
- **文档源**：读产品文档，提取待核实项——每项 = 编号 + 功能描述（原文）+ 出处段落
- **口述源**：把用户口述整理成等价条目，**复述确认**
- 两源可混合，统一编号后走同一确认流程；同时和用户对齐每项**实现判据**——什么算"实现"：API 存在 / UI 可达 / 数据流贯通 / 测试覆盖 / 配置生效

### 2. 核查计划
按模块/域聚类功能点（相邻的归同一代理，省重复扫描）；为每项列出预期证据锚点（路由 / 组件 / 数据表 / 配置键 / 测试名）。

### 3. 并行取证
**后台派发只读探索子智能体**（Explore / code-explorer，按聚类分组；未装则主智能体自查），每个代理的指令包含：
- 所辖功能点 + 各项判据 + 项目技术栈提示
- 证据返回格式：`文件:行` + 关键代码摘录（≤5 行）+ 置信度（高/中/低）
- 铁律：**只陈述找到的证据，禁止臆断"应该有"**

### 4. 逐项裁定
汇总证据，四态裁定：
- ✅ 已实现 / 🟡 部分实现（缺什么） / ❌ 未找到实现 / ⚠️ 实现但与描述不符（偏差点）
- **低置信度项必须二次复核**（换关键词/换代理再查一轮）后才允许下 ❌——漏报比多查代价高

### 5. 报告落盘
`.zdev/verify/<yyyy-MM-dd>-<主题>.md`：
- 总览统计（✅a / 🟡b / ❌c / ⚠️d）
- 逐项对照表：功能点（原文+出处） | 判定 | 证据（文件:行） | 差距说明
- **差距清单**（❌+⚠️+🟡 缺口汇总）——只列出不流转，转不转 zarchitect 由用户点名

## 边界
- 只读核查：可运行测试/构建作为辅助证据，不改任何源码
- 不开 change、不修复——差距修复走 zarchitect → zapply，由用户点名发起
- `.zdev/verify/` 是一次性核查产物：不 commit 不 push，历史报告删留随意（零机制依赖）
