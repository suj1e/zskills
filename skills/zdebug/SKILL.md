# zdebug

调试排查 skill:**收集症状 → 派发 debugger agent 深度调查 → 画图辅助理解 → 输出图文并茂的排查报告 → 如需修复则开 openspec change**。

## 何时触发
- 用户说"报错了"、"这里有问题"、"排查一下"、"为什么失败"
- 应用崩溃 / 进程退出 / 未捕获异常
- 测试失败（单元测试、集成测试、E2E 测试）
- 线上故障排查（500 错误、超时、数据异常）
- 诡异行为（功能不符合预期、数据错乱、状态异常）
- 性能劣化（响应变慢、内存上涨、OOM）
- 构建/打包失败（编译错误、依赖冲突）

## 工作流

### 1. 接单：明确症状
和用户确认：
- 什么时候出现？是否可稳定复现？
- 影响范围（单个用户 / 全量 / 特定场景）？
- 最近有没有改过相关代码或配置？
- 错误日志、堆栈跟踪、截图（如有）

### 2. 收集初步证据
- 读取错误日志、堆栈跟踪、错误码
- 查看相关代码路径
- 检查配置和环境（版本、依赖、环境变量）
- 如果是前端问题，检查网络请求、控制台输出
- 如果是移动端问题，检查 logcat/系统日志、截图

### 3. 派发 debugger agent 深度调查
将证据和症状整理后，**后台执行**派发 `debugger` 子智能体进行深度调查(不阻塞会话;调查完成通知到达后再继续整合)。

**必须包含的上下文**：
- 症状描述和复现条件
- 已收集的证据（日志片段、堆栈跟踪、错误码）
- 相关代码路径和文件
- 平台信息（Android / iOS / Web / 后端）
- 排查重点（调用链 / 数据流 / 配置 / 依赖）

**debugger agent 会返回**：
- 根因分析
- 调用链 / 数据流图
- 修复建议（多方案 + trade-off）
- 验证步骤

### 4. 画图（图文并茂，必须）
基于 debugger agent 的排查结果，使用 `diagram-design` 技能生成：
- 调用链图（sequence）—— 展示从入口到出错的完整路径
- 数据流图（data-flow）—— 展示数据如何流经出错点
- 架构图（architecture）—— 如果问题涉及多个服务/模块
- 内存分析图—— 如果是内存泄漏/OOM

图产出后放在项目目录下的 `docs/debug/` 或 `openspec/debug/`，并在排查报告中引用路径。

### 5. 整合报告
将 debugger agent 的排查结果整合成结构化报告，加上你收集的初步证据。

### 6. 开 Change（如涉及修复）
如果修复需要代码变更，执行 `openspec new change <yyyy-mm-dd>-<kebab-slug> --description "fix: ..."`，在 `openspec/changes/<slug>/` 下写入 `proposal.md`（问题描述 + 根因 + 修复方案）。
如果只需配置调整或简单修复，不需要开 change。
如果问题不是代码问题（环境问题、用户误操作等），不需要开 change。

### 7. 交付
输出结构化排查报告，交给用户或 craftsman 执行修复。

## 约束
1. 深度调查交给 debugger agent，主智能体负责整合和画图。
2. 排查报告必须附带图——调用链图或数据流图，没有图的报告视为不完整。
3. 必须基于证据（日志、堆栈、代码）下结论，不猜测。不确定的就写「待确认」。
4. 涉及安全问题（注入、权限泄露、数据暴露）立即标注为「高危」，不自行绕过或淡化。
5. 性能问题必须给出量化数据（响应时间、内存占用、请求量），不凭感觉说"变慢了"。
